## 1. Что умеет прототип

| Требование ТЗ | Как сделано |
|---|---|
| Тестовый набор данных | Три участка организаторов встроены. Свой набор загружается как JSON в формате `datasets/*.json`: меню участка → «Загрузить свой набор». Образец формата — там же, «Скачать этот набор» |
| Распределение заявок и порядок визитов | Вставка с сожалением (regret-2) → локальный поиск → LNS «удаление маршрута» |
| Ограничения: квалификация, время, транспорт | Единый оценщик маршрута `RouteEvaluator`; через него проходит любое решение, включая ручное |
| Карта | Leaflet + OpenStreetMap: маршрут цветом бригады, номер визита, авария — ромб, заявка без исполнителя — пунктирный круг |
| Кто, куда и когда едет | Список бригад с числом заявок и пробегом, расписание бригад по часам, маршрут бригады по порядку |
| События дня | Авария, новая заявка (в том числе точкой на карте), отмена, сход бригады; готовые сценарии, журнал событий, возврат к утреннему плану |
| Что изменилось после события | Новые, перенесённые, сдвинутые, снятые и отменённые заявки; км по бригадам до и после; на карте — затронутые бригады и прежние маршруты пунктиром |
| Объяснения | По заявке: проверенные ограничения и выбор бригады; по бригаде: маршрут; по заявке без исполнителя: причина, разбор по бригадам и что сделать |
| Метрики и сравнение с базовым | Показатели плана с разницей к базовому; экран «Сравнение с базовым»: бригады, суммарный пробег и пробег каждой бригады |
| Дополнительно (ТЗ §2.5) | Ручное переназначение с проверкой; «кто ещё мог бы взять» с приростом км; прогноз опозданий (запас до конца окна меньше 15 мин); базовый вариант на карте; выгрузка плана в CSV |

**Сценарий демонстрации (ТЗ §4):**
1. Открыть участок: на карте заявки по видам работ.
2. «Рассчитать план».
3. Маршруты на карте, расписание бригад внизу, показатели сверху.
4. Щёлкнуть заявку: «Почему эта бригада» и «Другие бригады».
5. «Событие дня» → готовый сценарий (авария, новое подключение, отмена в пути, сход бригады).
6. Панель «Что изменилось» открывается сама.
7. «Сравнение с базовым»: число бригад и пробег по каждой бригаде.

## 2. Схема решения

```
 CSV организаторов ──► python -m app.cli build-datasets ──► datasets/*.json
                                                                 │
 Браузер ◄────────── HTTP /api ──────────► FastAPI (backend/app/api/main.py)
 React + Leaflet                                 │
 (frontend/)                       ┌─────────────┴──────────────┐
                                   │ Solver: вставка, локальный │
                                   │ поиск, LNS                 │
                                   │ Replan: события дня, дифф  │
                                   │ Explain: объяснения        │
                                   └─────────────┬──────────────┘
                                                 │
                         RouteEvaluator (проверка ограничений, стоимость вставки)
                         TravelMatrix (время и км между точками по виду транспорта)
```

- **Интерфейс** — одностраничное приложение на React. Сервер отдаёт собранную версию из `frontend/dist`,
  поэтому интерфейс и API работают на одном порту.
- **Алгоритм** — библиотека без ввода-вывода в `backend/app/solver`. Построение плана, базовый вариант,
  перепланирование, ручное назначение и объяснения проверяют допустимость одним оценщиком маршрута.
- **Данные** — заявки и бригады трёх участков в JSON. Состояние дня (план, события, журнал) хранится в
  памяти сервера.

## 3. Ограничения

| Ограничение | Правило |
|---|---|
| Квалификация | Навык заявки входит в навыки бригады |
| Время | Работа начинается внутри окна заявки. Приехать раньше и подождать можно, начать раньше — нет. Закончить после окна можно, но дорога и работа должны уложиться в смену бригады |
| Транспорт | Если заявка требует тип транспорта, он совпадает с транспортом бригады |

Все три проверяет `RouteEvaluator` (`backend/app/solver/evaluator.py`), другой проверки допустимости в
коде нет. Парные ограничения «заявка — бригада» описаны классами в `constraints.py`: новое ограничение
добавляется новым классом. Тесты проверяют каждый план независимым валидатором
(`backend/tests/helpers.py::assert_plan_valid`).

## 4. Логика оптимизации

**Цель** сравнивается лексикографически, по разъяснениям организаторов:
1. больше выполненных заявок с учётом приоритета: авария 10, подключение 5, ремонт и дозаказ 3;
2. меньше задействованных бригад;
3. меньше км, плюс штраф за начало аварии позже 2 ч от поступления и штраф за переезды между Москвой
   и пригородом.

**Алгоритм:**
1. Вставка с сожалением (regret-2): сначала аварии, потом подключения, потом остальное. Внутри одного
   приоритета первой ставится заявка, которая потеряет больше всего, если не получит лучший вариант.
2. Локальный поиск: перенос заявки, обмен двух заявок, перенос цепочки из 2–3 заявок, разворот участка
   маршрута.
3. Доназначение оставшихся заявок.
4. LNS «удаление маршрута»: заявки самой лёгкой бригады раздаются остальным. Шаг принимается, только
   если ни одна заявка не потеряна.

Проверка вставки заявки в маршрут выполняется за O(1): для каждой точки маршрута хранится самое позднее
допустимое начало. Тест сверяет быструю проверку с полным пересчётом на случайных маршрутах.

**Модель времени.** Бригада начинает смену в своей стартовой точке. К следующему клиенту выезжает так,
чтобы приехать к началу окна; ожидание проходит в предыдущей точке. Время в пути зависит от транспорта
бригады (раздел 7).

Расчёт детерминирован: одинаковые данные дают одинаковый план на любой машине.

## 5. Метрики и базовый вариант

Обязательные метрики ТЗ:
- **число задействованных бригад** — бригады, у которых есть хотя бы одна заявка;
- **пробег** по каждой бригаде и суммарно, км.

Дополнительно считаются назначенные заявки, км на заявку, время в пути и реакция на аварии: сколько
аварий начато в пределах 2 ч от поступления.

**Базовый вариант (ТЗ §2.3):** заявки идут в порядке файла. Каждая достаётся первой по списку бригаде,
в конец маршрута которой она допустимо встаёт. Порядок визитов совпадает с порядком назначения.
Ограничения проверяет тот же оценщик.

Метрики видны в интерфейсе (полоса показателей и экран «Сравнение с базовым») и в консоли:
`python -m app.cli benchmark`. Команда с ключом `--update-readme` обновляет таблицу результатов в README.

## 6. Перепланирование в течение дня

Правила — по разъяснениям организаторов:

- **Начатая работа не прерывается.** Работа заморожена, если бригада уже выехала к клиенту, работает или
  закончила. Бригаду в пути не разворачиваем (наше допущение).
- **Новая обычная заявка** встаёт в свободный интервал. Заявки других бригад не переносятся; время может
  сдвинуться в пределах окон со штрафом за сдвиг.
- **Авария** ставится как можно раньше; ориентир — начать в течение 2 ч от поступления. Она может
  перестроить оставшуюся часть дня. Вытесненные заявки уходят другим бригадам, иначе получают причину
  «вытеснена аварией».
- **Отмена** освобождает бригаду, и в освободившееся время ставятся ранее неназначенные заявки. Если
  бригада уже ехала к клиенту, она доезжает и освобождается на месте. Отмена не считается неназначением.
- **Сход бригады:** выполненные и начатые работы остаются за ней, остальные раздаются другим бригадам.
- Если без этого не обойтись, на линию выводится бригада из резерва; в списке изменений она помечена.
- **Ручное назначение:** диспетчер выбирает бригаду, заявка встаёт на лучшее место в её маршруте. Если
  назначить нельзя, сервер объясняет почему: нет навыка, занята, смена не покрывает окно. Остальные
  маршруты не перестраиваются.

После любого события каждая заявка находится ровно в одном состоянии: назначена, не назначена с причиной
или отменена. Это проверяет тест с событиями каждые 30–60 мин с 10:00 до 20:00 на всех участках.

## 7. Данные

**Источник.** Синтетические CSV организаторов (кодировка cp1251, разделитель `;`) нормализует команда
`python -m app.cli build-datasets`: исходные файлы кладутся в `docs/Датасет/`, результат —
`datasets/{east,southeast,southcenter}.{orders,engineers}.json`. Для запуска достаточно JSON; исходные CSV
в репозиторий не входят.

| Участок | Заявок | Подключение | Ремонт | Авария | Дозаказ | Бригад |
|---|:-:|:-:|:-:|:-:|:-:|:-:|
| Восток (`east`) | 66 | 31 | 21 | 8 | 6 | 13 |
| Юго-восток (`southeast`) | 83 | 36 | 31 | 12 | 4 | 14 |
| Югоцентр (`southcenter`) | 56 | 28 | 25 | 1 | 2 | 13 |

**Единицы.** Время — `ЧЧ:ММ` и минуты от полуночи (`start_min`, `end_min`), длительность — минуты,
расстояние — км, координаты — широта и долгота в градусах (WGS 84).

**Заявка** (`*.orders.json`):

| Поле | Смысл |
|---|---|
| `id` | номер заявки |
| `work_type` | вид работ: `emergency` авария, `connection` подключение, `local` ремонт, `addon` дозаказ |
| `skills` | требуемый навык (из вида работ) |
| `priority` | `urgent` у аварий, `normal` у остальных |
| `window` | окно начала работ: 2 ч с чётного часа; у 11 аварий Юго-востока — весь день |
| `duration_min` | чистое время работ, мин |
| `required_transport` | требуемый транспорт или `null` |
| `location` | адрес, район, координаты |
| `bk_type`, `hd_type` | типы заявки в классификаторах BK и HD из исходного файла |
| `tech` | технология подключения (FMC/FTTB) и гигабит, если есть в исходном файле |
| `released_min` | когда заявка поступила (для событий дня), мин от полуночи |

**Бригада** (`*.engineers.json`): `id`, `name`, `skills` (1–3 навыка), `transport`, `shift` (смена),
`depot` (стартовая точка). Бригада — один исполнитель.

**Справочники:**

| Навык | Виды работ |
|---|---|
| `connection` — подключение и дозаказы | подключение, дозаказ |
| `local` — локальные работы | ремонт |
| `emergency` — аварийные работы | авария |

| Вид работ | Норматив, мин | Чистая работа, мин |
|---|:-:|:-:|
| Подключение | 90 | 70 |
| Авария | 100 | 80 |
| Ремонт | 50 | 30 |
| Дозаказ | 40 | 20 |

Нормативы — из файла организаторов «Нормативы.xlsx». В каждый входят 20 мин брони на дорогу; их заменяет
рассчитанное время в пути, поэтому в план идёт чистое время работы.

| Транспорт | Скорость |
|---|---|
| `car` — автомобиль | 30 км/ч |
| `transit` — общественный транспорт | 18 км/ч + 5 мин на посадку |
| `bike` — велосипед | 12 км/ч |
| `foot` — пешком | 4,5 км/ч |

Расстояние — по прямой × 1,35 (поправка на городскую сеть улиц).

## 8. Допущения

- Горизонт — один день, время московское. Возврат в стартовую точку не нужен, обед не планируется.
- Окно заявки — интервал начала работ. Каждая строка исходного файла — отдельный выезд.
- Для аварии с окном на весь день реакция отсчитывается от начала рабочего дня (10:00), для аварий,
  поступивших днём, — от момента поступления.
- Координаты адреса — центр района плюс детерминированный сдвиг до ±1,2 км. Для Каширы, Ступино и
  Домодедово стартовая точка бригады — её город, для остальных — офис участка.
- Бригады построены по списку исполнителей из контрольного файла организаторов. Навыки, смены
  (10–19, 11–20, 13–22) и транспорт заданы нами.
- Требуемый транспорт у части заявок задан синтетически.
- Бригада в пути к клиенту не разворачивается; сошедшая бригада заканчивает начатую работу.

## 9. Известные ограничения и развитие

**Ограничения прототипа:**
- Координаты приблизительные, расстояния — по прямой с поправкой, маршруты на карте — прямыми линиями.
- Смены по 9 ч короче реальных: у организаторов преобладает график 2/2 с длинной сменой. Из-за этого
  часть вечерних заявок остаётся без исполнителя, а на Юго-востоке в пределах 2 ч начинаются 3 аварии
  из 12: большинство аварий там приходится на Каширу, а аварийный навык есть у немногих бригад.
- Загруженные наборы и события дня хранятся в памяти сервера и пропадают при перезапуске.
- Исходные CSV организаторов через интерфейс не загружаются, только JSON в нормализованном формате.
- Оборудование бригад не учитывается.

**Развитие:**
- Геокодирование адресов и расстояния по дорогам (OSRM), маршруты на карте по улицам.
- Профили бригад из контрольного распределения: территории, смены 2/2, аварийные бригады.
- Второй движок (OR-Tools) и выбор лучшего варианта из нескольких.
- Учёт оборудования: запас на бригаду и проверка при перепланировании.
- Эксперимент с расширенными окнами (например, 10–14 вместо 10–12) как вариант для сравнения.

## 11. Структура кода

```
backend/app/
  domain/        модели: заявка, бригада, маршрут, план; справочники; события
  data/          загрузка CSV, нормализация видов работ и нормативов, бригады
  geo/           TravelMatrix, расстояние по прямой × 1,35, геокодер-заглушка
  solver/
    constraints.py   парные ограничения (навык, транспорт)
    evaluator.py     RouteEvaluator — проверка допустимости маршрута и стоимость вставки
    objective.py     цель и её параметры (SLA аварий, штрафы)
    search/          вставка, локальный поиск, LNS, базовый вариант
    replan/          разрез дня на момент события, правила событий, дифф, альтернативы
    diagnose.py      причины неназначения и оценка «сколько бригад не хватает»
    explain.py       объяснения по итоговому плану
    core.py          Solver — сборка шагов алгоритма
  api/main.py    FastAPI: участки, план, события, сценарии, альтернативы, загрузка набора
  cli.py         build-datasets | solve | benchmark
  serve.py       запуск сервера из скриптов run.bat / run.sh
backend/tests/   тесты: оценщик, солвер, перепланирование, API, загрузка данных
frontend/src/    React 19 + Vite + Tailwind 4 + Leaflet
  state/         состояние рабочего места диспетчера
  components/    шапка, показатели, списки, карта, расписание, панель справа, события, сравнение
  lib/           подписи, форматирование, палитра бригад, выгрузка CSV и JSON
datasets/        нормализованные данные трёх участков
```
